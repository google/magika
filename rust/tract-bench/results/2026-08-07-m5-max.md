# Apple M5 Max feasibility result

Date: 2026-08-07

## Environment

- Magika base commit: `94ffd1d`
- Host: Apple M5 Max, 18 cores, 128 GB memory
- OS: macOS 26.5.2 (25F84), arm64
- Rust: rustc 1.95.0, cargo 1.95.0
- ONNX Runtime: `ort 2.0.0-rc.12`
- tract: exact version `0.23.4`
- Build: release, one codegen unit, LTO, stripped
- Input: batch 1, features extracted from `README.md`

The CPU comparison below is the median of six 200-iteration trials. Backend order alternated
between trials with `--reverse`. Times are microseconds. Cold time is model load plus runtime
preparation; first is the first inference after preparation; the remaining columns follow ten
unreported warmups.

## CPU optimization follow-up

The follow-up removes three avoidable costs:

- the harness now spawns one tract execution state and reuses it like a long-lived Magika session;
- tract's optional Rayon matrix-multiplication executor is enabled, with two threads as the default
  after end-to-end sweeps of one, two, and four threads;
- conversion replaces the `[1, 2048, 257]` one-hot tensor and its first matrix multiplication with
  an equivalent 257-row embedding gather.

The gather cuts the profiled embedding path from roughly 0.39 ms (equality, cast, packing, and
matmul) to roughly 0.03 ms. It preserves the original maximum score difference of
`2.4883775e-9` and identical winning labels. The converter emits the rewrite deterministically.

The table below is the median of ten alternating-order 1,000-iteration release trials. The harness
was also corrected so `First` is the actual first inference after preparation; the initial table's
`First` values inadvertently measured the second inference after parity verification.

| Backend | Cold | First | Mean | p50 | p95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| ONNX Runtime | 11,001 | 2,317 | 1,763 | 1,724 | 2,064 |
| optimized tract CPU | 18,373 | 2,048 | 1,750 | 1,661 | 2,133 |
| tract change | +67.02% | -11.61% | -0.74% | -3.63% | +3.32% |

The optimized tract CPU path is effectively tied on warm mean, 3.63% faster at p50, and 3.32%
slower at p95. A separate interleaved thread-count sweep confirmed two threads beat one end to end
(median p50 1,717 us versus 1,858 us). Rayon costs 911,328 bytes versus the initial single-thread
tract executable, leaving the optimized CPU executable 14.54% smaller than the ORT executable.

## Dedicated compute-owner timing

The new execution prototype does not reuse the ORT async-session architecture. One dispatcher feeds
bounded queues; dedicated OS threads own non-`Send` states and return completion messages. The model
is prepared once as a `Send + Sync` runnable shared by all owners, while each owner spawns and retains
its own private mutable state.

An initial batch-8 sweep held the nominal compute budget to eight threads:

| Topology | ORT files/s | tract files/s |
| --- | ---: | ---: |
| 1 owner x 8 threads | 685 | 453 |
| 2 owners x 4 threads | 1,209 | 797 |
| 4 owners x 2 threads | 1,252 | 1,391 |
| 8 owners x 1 thread | 2,057 | 2,110 |

The exact crossover is noisy under sustained load. Across three alternating-order measurements, the
median 4 x 2 result is 1,422 files/s for ORT and 1,347 for tract (-5.2%); the median 8 x 1 result is
2,025 for ORT and 1,879 for tract (-7.2%). Twelve and sixteen single-thread tract owners regress in
the initial sweep, to 1,983 and 1,814 files/s. The important result is architectural: inter-batch
owner concurrency closes most of the tract gap, while adding threads inside one state does not.

Isolated `/usr/bin/time -l` runs show the RAM cost. A tract-only process uses 75.0 MB maximum RSS
with one owner and 405.8 MB with eight. Sharing one prepared runnable reduces the eight-owner peak
from 449.2 MB, but mutable state storage still dominates. Comparable ORT-only runs use 91.3 MB and
540.7 MB, so tract's eight-owner peak is about 25% lower, though neither is a lightweight default.

## Fixed plans and sustained batch-128 timing

After reading tract's canonical
[`pipeline.md`](https://github.com/sonos/tract/blob/main/doc/pipeline.md), the benchmark now follows
its actual optimization boundary. Portable NNEF stores the decluttered typed graph; target-specific
LIR/kernel selection is not serialized. `--fixed-batch` binds `N` before CPU `into_optimized()` or
before `MetalTransform` plus `into_optimized()`, so no symbolic dimension remains in a hot plan. A
physically fixed NNEF exported with `convert-model --batch 128` produces the same optimized operator
counts as binding the portable artifact before preparation.

The converter now recognizes both exporter-expanded tanh GELUs explicitly. tract's automatic
pattern expects a `Pow`, while this ONNX spells `x³` as multiply chains. The rewrite reduces the
fixed CPU plan from 88 to 68 nodes and the Metal plan from 136 to 100; Metal casts fall from 49 to
33. The plans contain two `GeluApproximate` or `MetalGeluApproximate` kernels. Batch-128 parity versus
ORT remains within `2.3841858e-7` on CPU and `1.5199184e-5` on Metal. A trial fused-softmax rewrite
reduced plan nodes further but regressed CPU throughput from about 626 to 478 files/s and was removed.

One paired release run of ten consecutive fixed batch-128 calls (1,280 files) produced:

| Backend | Mean batch latency | Files/s | Change from ORT |
| --- | ---: | ---: | ---: |
| ONNX Runtime | 187.5 ms | 683 | baseline |
| fixed/fused tract CPU | 218.5 ms | 586 | -14.2% |
| fixed/fused tract Metal (MLX/auto) | 131.7 ms | 972 | +42.4% |

Longer isolated Metal runs show substantial host-frequency and thermal variance. Loaded batch-128
samples range roughly 790-852 files/s, while a cold sample reached 977. MLX, MFA, and GGML are close
enough that run order can swamp their difference; GGML led the first sweep and lost the reverse
sweep. A fixed batch-1,280 plan delivered 799 files/s with MLX and 757 with GGML. One giant tensor is
therefore not faster than ten bounded batch-128 compute calls and has worse memory/latency bounds.

## CPU kernel-selection follow-up

The built-in plan profiler wraps tract's evaluator on one real input, matching upstream's advice to
use profile/cost dumps before optimizing. At fixed batch 128, convolution `Im2col` and `OptMatMul`
consume about 27.5% and 29.3% of execution; max reduction consumes another 15.2%. GELU fusion lowers
the one-run profiled total from 286.7 to 235.2 ms (18.0%).

tract 0.23.4 has a `LazyIm2col` lowering, but its source explicitly rejects batch greater than one
because its offset tables are single-batch. At fixed batch one, setting
`TRACT_LAZY_IM2COL_MIN_KERNEL=5` for Magika's width-five convolution selects it and lowers the
profiled total from 2.90 to 1.71 ms. In two alternating 1,000-iteration runs, tuned tract CPU reaches
636-652 files/s while ORT reaches 414-418 files/s. The harness now defaults this knob to 5 before
model preparation while preserving a caller override; fixed batch 128 correctly retains eager
`Im2col`. The production CPU architecture should prefer batch-one/small dedicated owner classes
until tract gains batched lazy im2col.

## ORT-optimized export experiment

ORT Level 3 is already the runtime's default online optimization. Serializing it offline increases
the ONNX from 3,163,737 to 3,163,953 bytes. tract can import that result, but the fixed/fused NNEF
produced from it is 2,917,218 bytes, 65 bytes larger than the 2,917,153-byte fixed/fused NNEF produced
directly from the original ONNX. ORT preprocessing adds no size or tract-plan advantage and is not
part of the deployment pipeline.

## Direct fused Conv1D CPU experiment

The batch-128 CPU bottleneck is not an unavoidable cost of tract's matrix kernels. A benchmark-only
`DirectFusedConv1D` operator now replaces Magika's exact Conv1D -> transpose -> GELU chain after
binding the fixed batch and decluttering the graph. It keeps tract's selected packed f32
microkernel, packs the constant weights once, supplies batched convolution panels on demand, adds
bias in the MMM fused-spec program, and applies tract's SIMD GELU in place. No eager `Im2col`
tensor is created. The optimized plan contains one `DirectFusedConv1D` and zero `Im2col` nodes.

Two counter-ordered release trials used five consecutive batch-128 calls each (640 files per
backend). This host showed severe frequency/thermal drift, so ranges and order are more honest than
a false single-number precision:

| Execution order | ORT files/s | eager-im2col tract files/s | direct fused tract files/s |
| --- | ---: | ---: | ---: |
| tract then ORT | 576 | 326 | 646 |
| ORT then tract | 404-481 | 303 | 549 |

Direct fusion beats the separately measured eager tract path by roughly 81-98% in both order
classes, and beats its paired ORT run by 12-36%. Maximum absolute score difference versus ORT is
`2.3841858e-7`, with identical winning labels. This overturns the earlier conclusion that fixed
batch-128 CPU must remain slower than ORT: the problem was tract 0.23.4's eager-im2col lowering,
not CPU math throughput.

The same operator does not beat tract's existing batch-one `LazyIm2col` specialization, so it stays
an explicit large-batch experiment rather than replacing all CPU plans. Also, “fused” has a precise
boundary here: convolution accumulation and bias run in the selected MMM microkernel, while GELU is
an in-place SIMD pass owned by the same graph operator. tract's current `FusedSpec` has no GELU
microkernel instruction. A production-quality follow-up should either add that instruction upstream
or fuse the immediately following position-wise max reduction so the large activation never needs
to leave a bounded scratch tile.

## Resident fixed-plan Metal pool

The realistic Metal architecture keeps fixed classes `1, 8, 16, 32, 64` simultaneously resident.
Each class loads the same portable NNEF, binds its own concrete `N`, applies `MetalTransform`, runs
target optimization, spawns a private state, and executes one warm-up inference. After that,
switching is a state lookup only. No CPU model plan participates in Metal-only routing.

Ceiling routing exposed why padding is the wrong default: a two-file request padded to class 8
managed only 208 files/s. Exact routing instead decomposes against resident classes (`2 = 1+1`,
`9 = 8+1`, `10 = 8+1+1`) and never pads when class 1 is present. A five-iteration release sweep
produced:

| Request | Metal route | ORT files/s | Metal files/s | Metal change |
| ---: | :--- | ---: | ---: | ---: |
| 1 | 1 | 479 | 571 | +19% |
| 2 | 1+1 | 537 | 566 | +5% |
| 3 | 1+1+1 | 468 | 548 | +17% |
| 4 | 1+1+1+1 | 503 | 530 | +5% |
| 5 | 1+1+1+1+1 | 556 | 548 | -1% |
| 6 | 1+1+1+1+1+1 | 510 | 533 | +5% |
| 7 | 1+1+1+1+1+1+1 | 573 | 559 | -2% |
| 8 | 8 | 513 | 837 | +63% |
| 9 | 8+1 | 598 | 792 | +32% |
| 10 | 8+1+1 | 587 | 752 | +28% |

Exact class 16, 32, and 64 reach 913, 918, and 928 files/s respectively, versus ORT at 563, 607,
and 615. Metal-only routing is therefore essentially tied or faster for requests 1-7 and clearly
faster from class 8 onward, while leaving CPU compute capacity free.

Preparing and warming all five Metal states takes about 327 ms in the paired release sweep. An
isolated `/usr/bin/time -l` run reports 67.6 MB maximum RSS and 169.7 MB macOS peak memory footprint.
This startup cost is intentionally paid once so no class has a first-use pipeline spike; before
explicit warm-up, the first class-16 request took 572 ms.

For CPU-only fallback, the direct fused fixed plans reach 686, 702, 724, and 743 files/s at classes
8, 16, 32, and 64, improving 32-63% over the built-in eager-im2col plans. The mixed CPU pool keeps
class 1 on tract's built-in lazy lowering and applies direct fusion only from class 8. It is not part
of the Metal-only request path.

## Conversion and integration blockers

- The deterministic NNEF archive loads with `tract-core` extensions only; it does not need the
  ONNX parser or ONNX-only tract-OPL registry at runtime.
- Conversion now rewrites the embedding and both GELU chains, replaces exporter-generated
  dynamic shape inputs with equivalent `TDim` constants, and removes two full-range slices whose
  sentinel end value tract otherwise propagates as a literal dimension. The checked artifact has
  input shape `[N, 2048]`.
- tract's state is mutable and not `Send`. The tract path must use the new bounded
  accumulator/compute-owner design, not reuse the ORT `num_tasks`/async-session architecture.
  Dedicated owner threads retain private states spawned from one shared prepared runnable;
  synchronous CPU work stays off Tokio.
- Owner count needs a platform- and memory-aware default. Eight owners are fastest on this host but
  consume about 406 MB peak RSS; 12 and 16 owners regress.
- `tract-metal` pulls `tract-gpu`, `tract-transformers`, and `tract-pulse-opl`, which explains much
  of the optional backend's footprint cost.

## Recommendation

Do not integrate tract into the production library yet, but continue the fixed-plan prototype.
Codec-equivalent model size is a wash and the deployable CPU harness remains only about 15% smaller.
On macOS, the clean next prototype is one Metal-only owner with resident, warmed classes
`1, 8, 16, 32, 64` and exact decomposition. It is competitive for requests 1-7 and substantially
faster from 8 onward without consuming CPU compute capacity. Direct fused CPU remains a strong
non-Metal fallback, not part of the macOS Metal request route. The next integration gate is a
bounded accumulator feeding that owner while preserving ordered results and clean shutdown.
